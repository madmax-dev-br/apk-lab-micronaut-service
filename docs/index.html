APK Lab Micronaut Service

Dois serviços Micronaut (Java 21) para rodar APKs Android reais num servidor com o runtime do APK Web Lab: um runner que carrega e opera o APK e uma fila que organiza quem usa os runners. Tudo o que o site faz nos Controles também pode ser feito pela API.

O que é

Runner

Sessões de APK com toda a configuração dos Controles: aparelho, rede (lista de hosts, redirecionamento, offline, proxy), permissões e localização, overrides de método, Activities ignoradas, mocks de endpoint, limites de evento e memória. Toque, digitação, intents, Recriar / Reabrir a Activity, a Tela pronta (espera, evento SSE e captura só quando a tela assentou), screenshots PNG, limites de layout, árvore Compose, ViewModels, Logcat e rede por SSE, plugins e diagnóstico.

Fila

Jobs declarativos (passos: iniciar, esperar texto/testTag ou a tela pronta, recarregar a tela, tocar, digitar, screenshot, limites de layout, campo de ViewModel, Logcat, rede, plugins) e leases interativos com proxy da API do runner. Prioridades, justiça entre clientes, capacidade lida do health dos runners, retentativas, cancelamento, progresso por SSE e retenção.

Mesma API do serviço Node

Os caminhos e corpos JSON são os do apk-lab-node-service: um cliente escrito para um funciona no outro, e a fila de um pode usar runners do outro.

Arquitetura

Cada sessão do runner é um processo node sidecar/vm-host.mjs. O sidecar carrega os módulos do bundle público (o mesmo que o site serve), cria o Worker da VM (runtime/apk-worker.js) num worker_threads Worker com um shim pequeno (globais de Worker, fetch e XHR síncrono só para arquivos do runtime) e o dirige com o próprio APKWorkerClient do bundle. O runner Micronaut cuida do que é de servidor: HTTP, autenticação, CORS, validação, limites, SSE, o processo e as falhas dele.

Por que um sidecar Node

A VM do APK Web Lab é JavaScript: módulos ES, WebAssembly (CanvasKit/Skia, ICU, SQLite, zlib, codecs) e semântica de Worker. Ela não roda dentro da JVM como está. As opções eram reescrever a VM em Java (fora de questão: o comportamento vem do runtime publicado e tem de ser o mesmo do site) ou hospedá-la num processo que já entende tudo isso. O Node 22+ entende: worker_threads, fetch, WebAssembly e módulos ES, e o mesmo shim já é usado pelo serviço Node.

  • Isolamento: um processo por sessão. Um crash, um loop ou falta de memória derruba só aquela sessão; o runner mostra o erro com as últimas linhas do sidecar e permite POST /sessions/{id}/restart.
  • Memória: --max-old-space-size no processo (RUNNER_SIDECAR_HEAP_MB) e resourceLimits no Worker da VM (RUNNER_VM_HEAP_MB, ampliado por memoryMiB da sessão até RUNNER_VM_HEAP_MAX_MB).
  • Ambiente limpo: o sidecar recebe só PATH, HOME, TMPDIR e o diretório do runtime; nunca o RUNNER_TOKEN nem outras variáveis do runner.
  • Direção futura (não implementada): GraalJS + GraalWasm poderiam hospedar a VM dentro da JVM, sem processo extra. Faltam a semântica de worker_threads/Worker, o desempenho de WebAssembly equivalente ao V8 e uma validação completa do runtime nesse ambiente.

Protocolo do sidecar

JSON lines: uma mensagem JSON por linha, nos dois sentidos. A stdout do sidecar é só protocolo; tudo o que ele, a VM ou um plugin imprimem vai para a stderr, que o runner registra (nível DEBUG) e guarda as últimas 30 linhas para mensagens de erro.

# runner -> sidecar (stdin)
{"id": 7, "op": "tap", "args": {"selector": {"testTag": "salvar"}}}

# sidecar -> runner (stdout)
{"event": "ready", "protocol": 1, "revision": "c6940189447d", "node": "v22.11.0", "pid": 4121}   # uma vez, runtime carregado
{"id": 7, "ok": true, "result": {"via": "semantics", "element": {...}, "snapshot": {...}}}
{"id": 8, "ok": false, "error": {"status": 404, "code": "element-not-found", "message": "...", "details": {"activity": "..."}}}
{"event": "logcat", "data": [{"seq": 41, "level": "W", "tag": "APKWebLab", "message": "..."}]}       # só com assinatura
{"event": "netlog", "data": [{"seq": 3, "method": "GET", "url": "...", "status": 200, "mockId": "m-..."}]}
{"event": "session", "name": "snapshot", "data": {"seq": 12, "activity": "..."}}
{"event": "plugin", "data": {"id": "observar-vm", "blocks": [...]}}
{"event": "fatal", "message": "..."}                                                              # antes de sair com erro
OperaçãoUso
initid da sessão, política do operador (hosts, plugins, memória) e limites; antes de tudo.
load{apkPath, config}: o APK vai como arquivo do diretório da sessão (nunca em base64 pelo pipe); a config é validada de novo pelos sanitizadores do próprio bundle.
launch, intent, back, tap, type, scroll, input, waitNavegação e entrada.
snapshot, layoutBounds, elements, composeTree, screenState, diagnostic, screenshot, elementScreenshotLeitura da tela; screenshots voltam como PNG em base64.
activity, viewModels, fragments, inspect, field, methodsInspeção da VM (as mesmas consultas dos plugins).
logcat, network, subscribeLeituras paginadas e assinatura dos canais de eventos.
updateConfig, restart, getConfig, permissionRequests, answerPermission, clearAppData, plugins, stats, shutdownO resto da API.

Limites e falhas: cada linha tem no máximo RUNNER_SIDECAR_MAX_LINE_MB (64 MiB) nos dois sentidos; uma requisição maior é recusada com 413 sem derrubar o sidecar, uma resposta maior vira o erro response-too-large, e uma linha inválida ou grande demais vinda do sidecar o encerra. Toda chamada tem timeout (RUNNER_OPERATION_TIMEOUT_S + margem; carga: RUNNER_LOAD_TIMEOUT_S); um sidecar que não responde é encerrado e a sessão fica crashed. Se o processo sai, as chamadas pendentes falham com 503 sidecar-crashed (com as últimas linhas da stderr), as seguintes com 409 vm-not-running, e POST /sessions/{id}/restart sobe um sidecar novo com o mesmo APK e a mesma config.

Início rápido

Requisitos: JDK 21 e Node.js 22+. O Gradle vem pelo wrapper.

git clone https://github.com/madmax-dev-br/apk-lab-micronaut-service.git
cd apk-lab-micronaut-service

# 1. o runtime do APK Web Lab (~114 MiB, cada arquivo conferido por SHA-256) em vendor/apk-lab
./gradlew fetchRuntime            # ou: node sidecar/fetch-runtime.mjs

# 2. o runner
export RUNNER_TOKEN=$(openssl rand -hex 24)
./gradlew :runner:run             # http://127.0.0.1:8081

# 3. em outro terminal: a fila, com um cliente e o runner registrado
export QUEUE_CLIENTS="eu:$(openssl rand -hex 16)" QUEUE_RUNNERS="http://127.0.0.1:8081" QUEUE_RUNNER_TOKEN=$RUNNER_TOKEN
./gradlew :queue:run              # http://127.0.0.1:8080
curl -s http://127.0.0.1:8081/health
# {"ok":true,"service":"apk-lab-runner","runtimeRevision":"c6940189447d","maxSessions":2,"available":2,...}

O runtime vem do repositório público do site, no commit fixado em sidecar/runtime.lock.json (revisão do build-info.json, lista de arquivos, tamanho e SHA-256). Uma publicação nova do site não muda o que este repositório roda. Para usar outra cópia do runtime (por exemplo, um dist/ que você construiu), aponte APK_LAB_RUNTIME_DIR para ela. node sidecar/fetch-runtime.mjs --check confere uma cópia existente; --base <url> baixa de um espelho (os hashes continuam valendo).

Docker Compose

export RUNNER_TOKEN=$(openssl rand -hex 24) QUEUE_CLIENT_TOKEN=$(openssl rand -hex 24)
docker compose up --build
curl -s -H "Authorization: Bearer $QUEUE_CLIENT_TOKEN" http://127.0.0.1:8080/stats

A imagem do runner é multi-stage: JDK para compilar, uma etapa Node que baixa o runtime fixado, e a imagem final com JRE 21 + o binário do Node 22, usuário sem privilégios. A fila guarda jobs e artefatos num volume (QUEUE_STORE=file). O runner fica só na rede interna do compose.

Autenticação

  • Runner: um token de operador, RUNNER_TOKEN. Envie Authorization: Bearer <token>; em GET também vale ?access_token=<token> (o EventSource do navegador não envia cabeçalhos). GET /health e GET / são públicos. RUNNER_AUTH=off desliga a autenticação: só para uso local, escutando em 127.0.0.1.
  • Fila: um token por cliente, QUEUE_CLIENTS="alice:token-da-alice:3,bob:token-do-bob" (o terceiro campo é o limite de jobs/leases simultâneos daquele cliente; o padrão é QUEUE_MAX_PER_CLIENT). Cada cliente vê só os próprios jobs e leases. A fila fala com os runners com QUEUE_RUNNER_TOKEN (ou um token por runner: QUEUE_RUNNERS="http://a:8081|tokenA,http://b:8081|tokenB").
  • Tokens são comparados em tempo constante. Use HTTPS (um proxy reverso) fora de uma rede confiável.

Testes

./gradlew test     # unitários: sidecar falso, runners falsos; sem rede, sem APKs

Os testes unitários cobrem a fila (prioridade, justiça, capacidade, retentativas, cancelamento, timeout, expiração de leases, retenção, store em arquivo), validação, autenticação, CORS, plugins desligados por padrão e o protocolo do sidecar com um sidecar falso (crash, timeout, linha grande demais, linha inválida, restart). Os testes de ponta a ponta rodam só com as duas variáveis:

APK_LAB_RUNTIME_DIR=$PWD/vendor/apk-lab APK_LAB_TEST_APK_DIR=/caminho/para/apks-de-teste ./gradlew test

Eles usam APKs sintéticos de teste (uma sonda de rede, um app Compose de exemplo), nunca APKs de terceiros, e não acessam a internet: as respostas vêm de mocks e o redirecionamento de host vai para um servidor local. O CI do GitHub roda só os unitários.

Relação com o serviço Node

O apk-lab-node-service roda a VM dentro do próprio processo Node do serviço. Este repositório tem a mesma API (caminhos, corpos, formato de erro {"error": {"code", "message", "details"}}, eventos SSE) e os mesmos passos de job; as diferenças:

  • Um processo sidecar por sessão (isolamento de crash e de memória por processo) em vez de um Worker por sessão dentro do serviço.
  • Configuração validada duas vezes: records Java com Bean Validation (chaves desconhecidas são erro 400) e depois os sanitizadores do bundle no sidecar.
  • Cabeçalhos HTTP são Latin-1: em X-APK-Config e X-Job use JSON ASCII ou base64url (os dois serviços aceitam).
